## What is CS2DemoKit

Today, we are proud to announce a new highly optimized, and high performance Counter-Strike 2 demo parsing tool that has been in the works for about 18 months thus far. CS2DemoKit aims to provide high quality, well maintained, and accessible tools for anyone in the Counter-Strike community to use, build upon, and leverage to build the next generation of analysis tools. Starting out CS2DemoKit set out to create high-performance libraries to read, work with, and analyze server side and POV (client side) demos from real matches from a variety of sources.

If you want to know more about the CS2OpenDev initiative and what our commitments are to the CS Community please take a look at our [CS2OpenDev Organization Introduction](../cs2opendev-organizaton/).

## What ships today

Three NuGet packages, versioned in lockstep, targeting `net10.0`, with no UI dependencies and nothing to install beyond the packages themselves:

| Package | What it gives you |
|---|---|
| `CS2DemoKit.Parser` | The demo parse pipeline: frames and net messages, 270-plus typed game events, entity tracking with tick seeking, and typed entity reads. |
| `CS2DemoKit.Analysis` | A rule-driven analysis engine over a parsed demo: state-graph evaluator, per-player stats, highlights, clip planning, and a 3D line-of-sight engine. |
| `CS2DemoKit.Analysis.Rules` | The rules language's semantic core — lexer, parser, canonical AST, resolver, typed checker and canonical hashing. Zero dependencies, for editors and validation services. |

`CS2DemoKit.Analysis` sits at the top of the dependency graph, so installing it alone pulls a known-good set of all three. The smallest useful thing you can write is about six lines:

```csharp
using CS2DemoKit.Parser;
using CS2DemoKit.Analysis;
using CS2DemoKit.Analysis.Yaml;

ParsedDemo demo = MemoryMappedDemoSource.ParseFile("match.dem");
AnalysisRun run = DemoAnalysis.Run(demo, YamlConfigLoader.LoadShippedEmbedded().Rulesets);
```

Four baseline rulesets — KAST, per-player stats, weapon stats, and post-plant multi-kills — are embedded in the assembly, so a consumer with no rules directory on disk still gets a working scoreboard out of the box. When you want different numbers you write a YAML file, not C#. The entire rating stack lives in those files, coefficients included, so "I disagree with how that is computed" is an edit rather than a fork.

On a ten-core machine, a 290 MB full match parses in about 384 ms and evaluates the four shipped rulesets in about 1.4 seconds. Those numbers, the corpus they came from, and the several ways they can mislead you are written down in `docs/perf/baseline.md` in the repo rather than rounded off for a headline.

## What can CS2DemoKit be used for

**Stats and scoreboards, without writing code.** The rules language is the main way in. You describe what you want measured in a small YAML file — count these events, sum this value, keep the max over the match — and the engine walks every round of the demo and produces the numbers. You cannot crash the parser from a rule file; the worst outcome is a validation error telling you what to fix, with a line and column inside the expression and a ranked "did you mean" list for typos.

**Match review and highlight reels.** Highlights are per-round achievements that come back stamped with a frame-clock tick, and `CS2DemoKit.Analysis.Clips` turns those into renderer-neutral clip windows — reach-back, coalescing, per-round grouping, the lot. Rendering the video is your problem. Deciding *which twelve seconds matter* is the part this does.

**Aim and movement analysis.** The `shot` and `shot_landed` views carry sixteen and twenty-one attributes respectively, including counter-strafe admission, spray segmentation, first-bullet detection, and — when you supply baked map geometry — how far the crosshair travelled from first contact and how much it overshot. This is the newest part of the toolkit and the part with the most caveats attached; see below.

**Interactive tooling.** The parser hands out every byte offset an inspector needs and none of the presentation: per-frame raw ranges, per-inner-message ranges inside a decompressed payload, on-demand decompression of a single frame, and an entity tracker you can seek to any frame index, snapshot, or peek at without disturbing. If you want to build a demo browser that shows the wire bytes beside the decoded entity diff, the API is shaped for exactly that.

**Rule tooling, without the engine.** `CS2DemoKit.Analysis.Rules` is deliberately BCL-only — no protobuf, no YAML, no evaluator, no demo parser. If you are writing an editor extension, a linter, or an upload-validation service, you can lex, parse, resolve, type-check and canonically hash a rule expression without dragging in anything that knows what a demo is.

**Batch pipelines.** Nothing in the library touches a UI toolkit or a filesystem convention you cannot override, and determinism is treated as a feature rather than an accident: parsing is deterministic in the input bytes down to the order of its own warnings, entity replay is deterministic in the frames, and the parallel geometry build produces a bit-identical tree at one thread and at thirty-two. Run the same demo twice, get the same answer twice.

**The boring compatibility work you would otherwise do yourself.** Tournament demos recorded through SourceTV are byte-identical to Valve matchmaking in the file header and use a different round-end event. The event every stats tool reaches for first does not fire at all in the demos we have studied. Positions are a cell index plus an offset, not a vector. A field that was never networked is not the same as a field that is zero. None of that is interesting work and all of it is load-bearing, and it is already done.

## What CAN'T CS2DemoKit be used for

Worth being blunt about, because several of these look like they should work.

**It is not a demo player.** No renderer, no 2D radar, no playback clock, no UI of any kind. It gives you the data a player would draw. Drawing it is a different project.

**It does not find or fetch demos.** No Steam integration, no match-history API, no download manager. You hand it a `.dem` file you already have.

**It does not ship map geometry.** Line of sight is recomputed from baked map collision triangles, because there is no usable "spotted" bit on the wire to fall back on. That geometry is Valve-derived and large, so it is distributed out of band rather than inside a NuGet package. What the package carries is the *convention* for finding a bake — an environment variable and a directory walk-up — and a clean "not available" answer when there isn't one. Without a bake, visibility-gated stats report zero rather than guessing, and the build emits a coverage row naming the stat, the attribute, and which prerequisite is missing.

**It does not know where the bombsites are.** Zone membership needs trigger volumes or baked zone geometry, and neither is in a demo file. You can register your own provider and address it from rules by name like any built-in, but the library will not pretend to resolve `BombsiteA` for you. The nav-mesh place name *is* available, which covers most of what people actually want.

**It is not an anti-cheat, and we are not going to make it one.** A demo is a recording of what the server networked, and several of the things people reach for when they want to prove something are not in it. The aim-punch columns are the clearest example: they do not currently decode to a real recoil kick — values come back clustered near ±90 degrees, which is not a recoil kick by any reading — so the framework rejects every value that column produces rather than reporting a 300-degree recoil residual as data. That is the right behaviour, and it is also exactly the sort of thing that gets quietly ignored when somebody wants a number more than they want a correct one.

**It cannot recover what was never networked.** `flash_duration` is the instructive case: the wire carries a latched duration rather than a live countdown, and the two fields that would let you compute remaining blind time are never sent at all. We established that over 230,856 pawn-frames rather than guessing. Where a value is not recoverable, the library says so instead of interpolating something plausible.

**POV demos decode partially.** A client-recorded demo sends deltas for entities the recording client never received a full update for. We skip those rather than throwing, which gives you a usable but incomplete entity replay. `EntityTracker.DeltaUnknownCount` is a public counter, so you can see how much of that happened before trusting per-tick entity values. Game events are unaffected either way — anything derived from kills, deaths, damage or shots is correct regardless of what the entity decoder did.

**It is not a server plugin, and it does not read a live connection.** The same messages that end up in a demo file are what the server sends clients during a match, so a live path is not architecturally impossible. Nothing in the library is wired for one today.

## What next for CS2DemoKit

`0.11.0` is on nuget.org now. We are pre-1.0 and the API does still move between minor versions; every break is written down in `docs/releasing.md` with its mechanism and its fix, because "adding an optional parameter is a compatible change" is true right up until it isn't.

Four things are in front of us, all of them items the repository already tracks as open rather than roadmap invented for a blog post.

**Evaluation is where the time is.** Parsing is 21% of a demo load and its one structural lever has been pulled. Evaluation is 72 to 81%, and roughly 30% of *that* is the garbage collector. The last round of work there — carrying only the per-pawn cells that changed, instead of a full readout every frame — took evaluation down 22% and total load down 17% across a fifteen-demo corpus, improving on all fifteen. There is more of that kind of win available.

**The aim-punch column needs to decode.** Until it does, spray-residual metrics measure the decode rather than the player, and we would rather say so in the documentation than ship a plausible number.

**CI needs a demo corpus.** The test suites run in CI against a committed four-round sample, which means the parity and determinism tests that matter most only run locally. Closing that is a matter of getting full-match demos somewhere CI can reach them without committing them to the repository.

**1.0 when the API stops moving.** Not on a date — when a release goes by without a compatibility note.

If you use it and something is wrong, missing, or worse than whatever you were using before, file it on [the GitHub repo](https://github.com/CS2OpenDev/CS2DemoKit/issues). A bug report with a demo attached is worth roughly ten without one.
